## Project Overview

Crypto Tab is a single-codebase application distributed as:

-   a website at `crypto-tab.com`;
-   a Chromium/WebKit Manifest V3 new-tab extension;
-   a Firefox/Gecko new-tab extension.

It displays live and historical cryptocurrency prices, a clock, theme controls, and user preferences.
The currently supported assets are Bitcoin, Ethereum, and more. Supported chart periods
are one hour, one day, one week, one month, one year, and all time.

The project intentionally has no frontend framework, module bundler, or transpilation step. Runtime code
is loaded as ordered browser scripts and shares the `App` namespace.

## Runtime Architecture

Keep the price-data flow unidirectional, with one repository owner per platform:

```text
Website:   Crypto UI -> PriceRepositoryClient -> PriceRepositoryFactory -> SuperRepo -> PriceApi
Extension: Crypto UI -> PriceRepositoryClient -> background worker -> PriceRepositoryFactory
                                                      -> SuperRepo -> PriceApi
```

-   `src/js/script.js` is the application entry point.
-   `src/js/crypto.js` owns active token/period state, rendering, request-generation guards, the single
    refresh timer, and lifecycle cleanup.
-   `src/js/cryptoTokens.js` is the source of truth for supported tokens, periods, display names, defaults,
    validation, and API endpoint paths. It uses `globalThis.App` because it also runs in an extension
    background context.
-   `src/js/storageMigration.js` owns versioned, idempotent extension storage migrations.
-   `src/js/priceApi.js` validates requests and API payloads, performs the remote request, and normalizes
    numeric strings into finite numbers.
-   `src/js/priceRepositoryFactory.js` owns SuperRepo instances, cache policy, response mapping, stale-cache
    fallback, and the repository result contract.
-   `src/js/priceRepositoryClient.js` keeps the UI platform-agnostic. Website requests use an in-page
    repository factory; extension requests are delegated to the background worker.
-   `src/js/background.js` owns the extension repository factory and returns serialized repository results.
-   `src/js/chart.js` owns Chart.js setup and chart rendering.
-   `src/js/settings.js` abstracts persisted settings.
-   `src/js/settingsPanel.js` owns settings-panel interactions, but token persistence remains owned by
    `Crypto.changeCryptoType()`.
-   `src/js/browser-extension-api.js` provides the browser API compatibility layer.

Script order in `src/index.html` is significant. When adding a runtime file, place it after its
dependencies and before its consumers.

## Platform Boundaries

-   Website requests use direct `fetch()` calls.
-   Extension requests use runtime messaging and are executed by the background worker/script.
-   Website persistence uses `localStorage`.
-   Extension persistence uses `browser.storage.local`.
-   WebKit builds use a Manifest V3 service worker.
-   Gecko builds use background scripts generated by the manifest preprocessing step.

Do not make website code depend on an extension runtime receiver. Do not access Chrome-only APIs directly
from shared UI code when the compatibility layer or `window.browser` should be used.

## Data and Cache Invariants

-   Repository keys must be unique per token and period and remain versioned, currently
    `prices-v2:<token>:<period>`.
-   Current-price (`NOW`) data expires after 3 minutes.
-   Chart data expires on the next 5-minute clock boundary for `ONE_HOUR` and `ONE_DAY`, and the next
    15-minute boundary for `ONE_WEEK`, `ONE_MONTH`, `ONE_YEAR`, and `ALL`. The current hour/day/month
    average can still change; chart point spacing does not imply that the current point is final.
-   Keep refresh policy and next-check calculations in `CryptoTokens`, shared by repository owners
    and the UI. The single 30-second UI interval checks the active repositories when the tab is visible.
-   Repository results use this stable contract:

```js
{
    data,
    error,
    isStale,
    lastFetched,
    ok,
    repositoryKey,
    source,
}
```

-   `source` is one of `network`, `cache`, `stale-cache`, or `none`.
-   Expected network/cache failures should be represented by the result contract, not mixed into UI logic.
-   Never cache an unsuccessful, empty, or structurally invalid API response as fresh data.
-   Preserve stale valid data when a refresh fails.
-   SuperRepo 2.1.4 can retain a rejected request as pending. After a failed request, evict only the
    in-memory repository instance so a future refresh can retry; do not erase its persistent stale cache.
-   Numeric strings must be normalized at the PriceApi boundary. Downstream UI and chart code should receive
    finite numbers.
-   Prices are formatted with `Intl.NumberFormat`; preserve enough fractional precision for low-priced
    assets.

Maintain one authoritative SuperRepo cache per platform. Website pages own their local cache; the extension
background context owns the shared extension cache, and extension pages must not create a competing cache.
Persist extension cache state in `browser.storage.local`; treat the worker's in-memory instances as an
optimization that can be rebuilt after service-worker suspension.

## Async and UI Invariants

-   Keep exactly one refresh interval for the application lifecycle.
-   Refresh the active repositories; do not merely repaint the “last updated” label.
-   Preserve request-generation checks so a slow response for a previously selected token or period cannot
    overwrite the current UI.
-   Track status by repository key (`token:period`), not with global stale/error flags.
-   Keep rendering concerns in `Crypto` and fetching/caching concerns outside it.
-   Treat token and period values loaded from storage as untrusted and validate them through `CryptoTokens`.
-   Clear or update period-dependent UI immediately when the active context changes.
-   Keep product-facing copy inclusive of all supported cryptocurrencies; do not regress it to Bitcoin-only
    wording.

## Adding or Changing a Token

1. Update `src/js/cryptoTokens.js`; the settings dropdown is populated from this registry.
2. Confirm the API exposes `<token>/<period-path>` for every chart period and `NOW`.
3. Verify current-price and chart payloads pass PriceApi normalization.
4. Exercise website and extension transports.
5. Verify cache keys remain isolated from every other token and period.
6. Test rapid switching between at least three tokens to detect stale-response races.
7. Check formatting for both high-value and sub-dollar prices.
8. Update product metadata only when the public supported-asset description needs to change.

## Source and Generated Files

-   Edit source files under `src/`; never edit `dist/` by hand.
-   `dist/` and `node_modules/` are ignored and disposable.
-   Every build starts by cleaning only its target directory so deleted or renamed files cannot leak into the
    package.
-   `src/manifest.json` is a template containing `@@background`; it is not valid standalone JSON. Validate
    the generated manifests in `dist/extension-webkit/manifest.json` and
    `dist/extension-gecko/manifest.json` instead.
-   Do not remove or rename manifest placeholders without updating `gulpfile.js` preprocessing.

## Extension Permissions and Releases

-   Request the narrowest permissions required by current functionality.
-   The extension currently requires `storage` and host access only to `https://api.crypto-tab.com/*`.
-   Adding a required permission or a new host can disable the extension after auto-update until users accept
    the new warning. Do not expand `permissions` or `host_permissions` without explicit approval and release
    impact analysis.
-   Removing obsolete permissions or narrowing access is preferred.

## Development Commands

Use Node.js 22 or newer and install dependencies with `npm install` (or `npm ci` in a clean environment).

The website is usually already running at `http://localhost:8000/` for local testing. Check and reuse
that server before starting another one.

```bash
npm run build:website
npm run build:extension:webkit
npm run build:extension:gecko
```

Watch modes:

```bash
npm run build:website:watch
npm run build:extension:watch:webkit
npm run build:extension:watch:gecko
```

Generated targets:

-   `dist/website/`
-   `dist/extension-webkit/`
-   `dist/extension-gecko/`

## Code Style and Change Discipline

-   Follow `.prettierrc`: 4-space JavaScript indentation, 2-space HTML/JSON indentation, single quotes,
    semicolons, and a 100-character print width.
-   Follow the existing style in build configuration files and avoid unrelated mass-formatting.
-   Prefer plain browser APIs and small focused functions over new abstractions or dependencies.
-   Keep functions and state ownership explicit; avoid duplicated settings writes or data transformations.
-   Use DOM APIs such as `textContent` and element creation for dynamic text.
-   Preserve unrelated user changes in the working tree.
-   Do not commit, push, publish, modify a PR, or edit store listings unless explicitly requested.
-   Keep commits focused and describe user-visible behavior, architecture, cache semantics, and build/release
    effects when relevant.
